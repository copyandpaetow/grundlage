parser bench

Calls getParsedTemplate directly — no mount, no render. A parse is a rounding error inside a mount and would not be visible through the render path; end-to-end cost belongs to perf.

This page measures per-character work only. Compile plus cold-tier execution is roughly 95% of what the parser costs on first load, it scales with the parser's own shipped bytes rather than with its input, and it is not measurable in an already-warm page. Read that half from the gzip size of the built parser instead. A "cold" number printed here would be a false write.

Every shape holds one axis still and moves another. hole density fixes characters and varies holes, twice: once with the holes adjacent inside one element, once with an element per hole. The first slope is the cost of a hole, the second adds the cost of the element that carries it, and the intercept is the scanner with no holes at all. part length fixes holes and varies characters — flat ns/char means slicing is linear and cheap. template count splits the same 48k characters across 1 to 256 templates, separating per-template fixed cost from per-character cost. hole kind gives every binding lane equal holes and characters, including the <style> path and the comment lane the site itself never exercises. control is the 33 templates recorded off this site: a win on synthetic shapes that loses here is tuning for a phantom.

Each pass parses fresh TemplateStringsArray wrappers so the parse cache always misses. Repeats per pass are chosen so a pass clears the 100µs clock granularity, results are best-of-N, and the numbers are normalized — absolute pass time is an artifact of the repeat count.

Two conditions mark a row VOID instead of reporting a number, because each one means the timing is not evidence: cache hit, the parse never happened; unstable timing, the median pass is more than twice the best, so one pass measured something the others did not and best-of-N no longer holds. A void row is also dropped from the ns/hole fits — a fit is where one bad row disappears into a headline number.

A retained-heap reading of zero or less is impossible and is dropped to — on its own, without voiding the row: it costs the B/tmpl column, not the timing. A whole column of — means Chrome is running without --enable-precise-memory-info.

An A/A run of the equivalent playwright rig against identical code resolved work to about 8% and retained heap to about 23%. The delta column dims anything inside that floor: it is noise, not a result. A refactor wins when gzip bytes drop, the recorded control does not regress, and ns/char stays inside the floor. Run Chrome with --js-flags=--expose-gc --enable-precise-memory-info for trustworthy heap numbers.
