render bench

Calls patchInstance directly on a mounted instance — no driver, no microtask, no rAF, no paint. The unit is one live-binding commit, which is where the commit-path findings live. Frame-level cost belongs to perf, the same split parser bench draws.

A pass never yields, so style recalc and layout land after it has been timed. That is deliberate: a commit-path change moves JS work, and recalc would bury it under a cost the change cannot touch. These numbers are the JS half of a frame, not the frame.

Every lane runs twice, because combinedPartsHash runs before claimHashChange. unchanged is what a binding costs when nothing moved — the gate hash and nothing else, which is the majority case in a real update. changing adds composeParts and the write. A finding that only shows up in one of the two is a finding about one of them.

The rows are not the point; the gaps between them are. staticNameAttribute minus content on the unchanged rows is P13's whole target: a text gate is one hashValue, an attribute gate adds combinedPartsHash over the name and one combineOrderedHash, and nothing else separates them. composedNameAttribute minus staticNameAttribute puts one real hole in that same gate, for scale.

customElements.get is timed on its own rather than subtracted out of a lane, because subtracting it does not work: once an anchor has a dash in its name Blink runs its own slower attribute path, and no cache in this library removes that. The custom-element gap is printed anyway and labelled for what it is. Note also that isDeclaredPropName returns on localName.includes("-") first, so a plain element never reaches the registry, and that the gate closes before the write path runs at all — an unchanged binding never looks anything up.

B/commit is heap growth over a pass, a lower bound — a minor collection inside the pass hides some of it. Read it by comparison, not absolutely: equal growth on staticNameAttribute and composedNameAttribute means composing a hole-free name allocates nothing, which is the claim that result += part over one string part quietly rests on.

Run it under 20× CPU throttle in DevTools; that is the old-device approximation the measuring contract assumes. Chrome needs --enable-precise-memory-info for the heap column to mean anything. A row marked VOID is not evidence: the churn axis did not behave, the passes did not agree, or calibration sized the pass off a cold reading and left it too short to resolve. A gap printed under resolution is not a small finding, it is no finding.
